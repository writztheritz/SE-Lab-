# Lab 1: Requirements Engineering & UML Use-Case Modelling

## Objective
Elicit requirements from an assigned scenario, document clear and verifiable functional and non-functional requirements, and model system behaviour using a UML Use-Case Diagram and a detailed use-case flow.

## Tools
- draw.io, Lucidchart, or another UML modelling tool
- Word or Excel for the requirements table
- A document editor for the use-case flow

## Lab Activities

### 1. Review the Assigned Scenario
- Identify the system's main functions and constraints.
- Determine user goals and interactions with external systems.
- Identify functional and non-functional requirements.

### 2. Document Requirements
Prepare a requirements table containing exactly:
- Five Functional Requirements: FR-001 to FR-005
- Two Non-Functional Requirements: NFR-001 and NFR-002

Each requirement must include:

| Field | Description |
|---|---|
| Requirement ID | Unique identifier for the requirement |
| Type | Functional or Non-Functional |
| Description | A clear statement beginning with "The system shall..." |
| Priority | High, Medium, or Low |
| Acceptance Criteria | Measurable conditions for a pass/fail decision |
| Rationale | Brief justification for the requirement |
| Comments | Peer-review feedback and suggested improvements |

### 3. Review and Refine Requirements
Exchange the requirements table with a peer and evaluate:
- Clarity: Is the requirement unambiguous?
- Testability: Can it be verified using measurable acceptance criteria?
- Relevance: Does it match the assigned scenario?

Revise the requirements based on the feedback.

### 4. Identify Actors and Use Cases
From the refined requirements, identify:
- At least three actors
- At least five use cases

Actors may represent people, devices, or external systems that interact with the application.

### 5. Create the UML Use-Case Diagram
The diagram must include:
- A clearly labelled system boundary
- Actors and use cases
- Associations between actors and use cases
- Use-case identifiers and titles, such as UC-01 to UC-05
- At least one «include» or «extend» relationship

Use «include» for required, reused behaviour and «extend» for optional or conditional behaviour.

### 6. Write a Use-Case Flow
Choose one key use case and document:
- Main Success Scenario: the step-by-step successful interaction
- Alternate Flow: at least one exception or alternative path

### 7. Finalize and Export
- Review the requirements for completeness and testability.
- Check the UML diagram for correct notation.
- Export the Use-Case Diagram as a PDF.
- Export the Use-Case Flow as a PDF.
- Upload the deliverables to this lab folder.

## Deliverables
1. Requirements table with five functional and two non-functional requirements
2. UML Use-Case Diagram
3. One-page Use-Case Flow with a Main Success Scenario and at least one Alternate Flow

## Learning Outcomes
- Elicit and document clear, testable requirements.
- Define measurable acceptance criteria and justify priorities.
- Identify actors and model system functionality.
- Apply UML use-case notation and relationships.
- Describe successful and alternate interaction flows.
- Improve requirements through peer review.
- Organize requirements in a structured, SRS-style format.
